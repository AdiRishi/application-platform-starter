---
title: Mirror tests in a tests/ directory beside src/
description: Every tested workspace keeps production and test code in separate TypeScript projects, with tests/ mirroring src/.
sidebar:
  label: Test mirroring
---

Every workspace with tests keeps them in a `tests/` directory that mirrors its `src/` directory. Tests for `workers/processor/src/artifacts/profile-csv.ts` live at `workers/processor/tests/artifacts/profile-csv.test.ts`. Tests for `apps/web/src/features/artifacts/profile-detail.tsx` live at `apps/web/tests/features/artifacts/profile-detail.test.tsx`.

Use `.test.ts` for a module tested without deployed or emulated infrastructure. Use `.integration.test.ts` when the test crosses an infrastructure boundary such as D1, R2, a Queue, a Durable Object, a Worker handler, or a live cloud resource. The path still names the production module that owns the behavior.

The mirror rule has three explicit exceptions:

- `tests/setup.ts` registers runner hooks shared by every test file in the workspace.
- `tests/env.d.ts` declares runner context visible only to tests.
- `tests/support/` and `tests/fixtures/` contain reusable test infrastructure and data. A support module does not contain tests.

Do not create a general `helpers.ts` or `utils.ts`. Name support files after the boundary they configure, such as `fixtures/profile-session-worker.ts`.

The production and test trees are separate TypeScript projects. `tests/tsconfig.json` extends the workspace's production configuration and adds only the types the test runner needs. The production project does not include test files, Vitest configuration, test setup, or test-runner globals. Each tested workspace's `typecheck` script checks both projects.

The test runner follows the public boundary under test:

- A pure Effect test uses [`@effect/vitest`](https://github.com/Effect-TS/effect/tree/main/packages/vitest) and `it.effect`. The runner supplies test services and closes a fresh `Scope`; the test does not add another `Effect.scoped` wrapper.
- Infrastructure integration tests live under `infra/tests/`, mirroring the stack and resource graph that owns their lifecycle. Use [`alchemy/Test/Vitest`](https://alchemy.run/testing/testing-a-stack/) to deploy a stack once in `beforeAll`, exercise HTTP or RPC interfaces, and destroy it in `afterAll`. Alchemy owns bundling, bindings, migrations, queues, and local runtimes.
- Declare `Test.make` in each integration file. Set Vitest's `sequence.hooks` to `"list"` so the explicit destroy hook runs before Alchemy's deferred fallback cleanup.
- Local suites use `dev: true`, local state, and a unique `test-*` stage. `pnpm test:infra-live` runs the public application suite with `dev: false`. Its configuration supplies the mode through Vitest's `provide`; test bodies do not change environment variables.
- Drive API RPC with Alchemy's `rpcClientLayer` and the application's serialization. Drive native Durable Object RPC through an Alchemy-declared consuming Worker. Test fixtures use real resources and public bindings. Seed stored recovery cases with Alchemy Actions.
- Use `getWhenReady` for startup and bounded Effect schedules for asynchronous results. Retry only failures the application defines as retryable. Assertions must still fail if the operation never reaches its expected terminal state.
- A React test uses [React Testing Library](https://testing-library.com/docs/guiding-principles/) and asserts visible behavior through roles, labels, and user interactions. Shared DOM cleanup lives at `apps/web/tests/setup.ts`.

Tests protect behavior through a public interface. They use real internal collaborators, replace only external system boundaries, and compare results with independently known values. They do not assert private helpers, internal call order, or mock call counts. These rules follow the test seams and anti-patterns in [Matt Pocock's TDD skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md).

The rejected alternative is colocating tests inside `src/`. Colocation makes the nearest test easy to spot, but it puts production and test files in one tree and encourages test-only types to leak into the production project. Mirroring preserves the same path relationship without weakening the boundary.
