---
title: Organize Workers by owned capability
description: Worker entrypoints compose capability modules, while shared schemas define typed HTTP RPC between Workers.
sidebar:
  label: Worker modules
---

Each Worker keeps `src/index.ts` as its runtime adapter and composition root. It may export Cloudflare entrypoints and Durable Object classes, but it does not own application behavior. Capability folders own that behavior:

```text
workers/processor/
├── src/
│   ├── index.ts
│   └── artifacts/
│       ├── profile-job.ts
│       ├── profile-session.ts
│       ├── profile-csv.ts
│       ├── repository.ts
│       ├── rpc.ts
│       └── errors.ts
└── tests/
    ├── setup.ts
    ├── env.d.ts
    └── artifacts/
        └── ...
```

Create another capability folder when the Worker gains behavior with a different domain owner. Do not add production files beside `index.ts`, and do not split a capability into generic `services/`, `repositories/`, or `utils/` directories. A file name describes its role inside its capability.

Schemas used by more than one runtime belong in `@repo/contracts`. The processor's `ProcessorRpcs` group is the source of truth for its callable interface. The processor serves that group at `/rpc` through Effect RPC with JSON serialization. The API uses the same group to derive `ProcessorClient`, backed by the existing Cloudflare service binding. HTTP remains the transport, while callers use typed Effect functions and do not construct URLs or decode JSON.

Tests replace the remote Worker boundary, not modules inside a Worker. Use `RpcTest.makeClient` for an in-memory client backed by real RPC handlers. Keep one Workerd integration test that sends the shared RPC contract through the HTTP handler so the transport and serialization stay covered.

Durable Object RPC methods return contract types rather than JSON strings. Each SQLite-backed object owns a `_sql_schema_migrations` table and applies ordered migrations inside `blockConcurrencyWhile`. The binding interface is defined once in `infra/src/worker-bindings.ts`.

Queue consumers distinguish malformed messages from processing failures. A malformed message cannot succeed on retry, so both the primary and dead-letter consumers acknowledge it after logging. Processing and storage failures follow the queue's configured retry and dead-letter policy. The starter does not prescribe leases or recovery workflows for an application that replaces the sample processor.

Worker TypeScript projects extend `@repo/tsconfig/worker.json`. Each Worker adds Cloudflare declarations and Node declarations because the deployed compatibility configuration enables `nodejs_compat`. Browser libraries remain in `web.json`, and Vitest declarations remain in `tests/tsconfig.json`.

The rejected design keeps application behavior in a flat `src/` directory and exposes hand-written internal HTTP endpoints. That layout makes ownership less clear as features accumulate, and the private protocol duplicates schemas, request construction, decoding, and error mapping in each caller.
